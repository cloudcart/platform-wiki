# Invoice

## Identity

An **Invoice** is the formal accounting document the merchant issues against an [[order|Order]] — a customer-facing tax record that proves the sale, declares VAT, and feeds the merchant's bookkeeping. It is generated by the configured **Invoicing provider** — CloudCart's built-in renderer, or an external system such as Szamlazz that takes issuance over entirely (see [[settings-invoicing]]) — and downloaded as a PDF. The platform assigns a fixed `invoice_number` + `invoice_date` pair and stamps it onto the parent Order. Once consumed, a number can never be reassigned — invoices are part of the merchant's permanent tax audit trail.

An Invoice has no record of its own: it is the rendered PDF plus the `invoice_number` + `invoice_date` fields on the Order. PDFs are not archived — re-downloading always re-renders fresh from current Order + [[settings-invoicing]] data.

An Invoice is distinct from a **Receipt** ([[order]] → receipt action), a simpler proof-of-payment document, and from a **Credit Note** ([[credit-note]]), which reverses all or part of an existing Invoice. An Invoice can be reversed by **one whole-order credit note**, or by **several partial credit notes** issued through the order's returns — as long as the total credited stays within the order total. See [[orders-credit-numbering]].

**An invoiced order is frozen.** Once an invoice number exists, the order can no longer be edited at all — no line-item changes, no price changes, no added products ([[orders-details-products]]) — and its prices can no longer be converted from BGN to EUR ([[orders-details-actions]]). Corrections go through a return / credit note, or through a new order.

## Aliases

- **Invoice** — the canonical merchant-facing term in the admin UI, sidebar (**Invoices** cross-order list), order details, and customer emails.
- **Tax invoice** / **Customer invoice** / **Order invoice** — informal merchant phrasing depending on context (accounting vs. customer service).
- **Фактура** / **Данъчна фактура** — Bulgarian terms; "Данъчна фактура" emphasises the VAT-document nature for BG accounting.
- Invoice numbers in the admin, emails, and downloaded PDF use the merchant's configured format (e.g., `INV-2026-000123`), built from the three separate `invoice_number_formatting_prefix` / `_padding` / `_suffix` settings in [[settings-invoicing]]. There is no single pattern field.

## Key Attributes

| Attribute | What the merchant controls | Notes |
|-----------|----------------------------|-------|
| **Invoice number** (`invoice_number` on the order row) | Format configured in [[settings-invoicing]]; manual override when `invoice_number_type = 2` | Next number in the sequence. **The numeric sequence is immutable once assigned**, but the formatted display is composed live from `invoice_number_formatting_prefix` + `_padding` + `_suffix` — changing padding mid-year re-pads even historical Invoices on re-download. |
| **Invoice date** (`invoice_date` on the order row) | n/a in the admin (set automatically at issue time) | Issue timestamp — distinct from the Order's `date_added`; used as the tax point. Not editable from any admin screen, but it **is** writable through the orders endpoint of the JSON-API — see [[api-orders]]. |
| **Issuer company block** | Configured in [[settings-invoicing]] — `company_name`, `company_vat`, `company_bulstat`, `company_mol`, `site_phone`, `country`, `site_city`, `site_street`, `postal_code` | Pulled from **live** settings on every re-render — no issue-time snapshot. Editing company info later changes future re-downloads of OLD Invoices too. The merchant's own VAT is NOT validated against VIES. |
| **Customer billing block** | Comes from the Order's billing address (`orders-address-edit`) | First/last name, company name, VAT number, billing address (street, city, postal code, country). Edited via the Order, not the Invoice. |
| **Line items + tax breakdown** | n/a (computed from Order line items at render time) | Product name, SKU/EAN (optionally a barcode), quantity, unit price, line total, per-line VAT. Computed per the store's gross/net mode (`vat_included` on the Order). |
| **Totals** (subtotal, discount, shipping, tax, grand total) | n/a (computed from the Order at render time) | Stored as integers in cents on the Order; re-renders pick up any later Order edits. |
| **Currency** | n/a (copied from the Order's `currency` at order time) | Locked on the Order at create time — always renders in the Order's stored currency. The **Convert prices to EUR** button on [[orders-details]] is NOT a display toggle: it permanently rewrites the Order's amounts at the fixed rate and sets its currency to EUR, and it is **rejected outright once the Order has an invoice number**. So an invoiced BGN Order can never be converted. |
| **Locale** (rendering language) | n/a (copied from the Order's `locale`) | Renders in the customer's storefront language at order time, falling back to site primary then admin language. Labels come from [[settings-translations]]. |
| **Payment method block** | Toggled via `show_payment_details` + `show_payment_description` in [[settings-invoicing]] | The merchant's IBAN / payment-method description. Reflects the current config at render time. |
| **Header rows** (`custom_header_text`) | Configured in [[settings-invoicing]] | Free-form key/value lines at the top (e.g., "Reg. №: BG12345"). |
| **VAT exemption reason** | Inherited from store / order tax config | Free-text legal reason on B2B / EU reverse-charge invoices (e.g., *"Reverse charge — Article 196 of Council Directive 2006/112/EC"*) when line items qualify. |
| **HTML template** (`invoice_body`) | Edited via the HTML templates tab in [[settings-invoicing]] | Empty → default template renders; populated → custom HTML with placeholder substitution. No syntax validation — broken HTML renders as broken PDFs. |
| **Items default classes** (`invoice_items_default_classes`) | Not configurable — a read-only reference list | The CSS class names the default invoice markup already uses, listed in [[settings-invoicing]] so a template author knows which hooks exist. Nothing is filtered at render time; a custom template may use any class. |
| **External number source** | Set by the installed App when `invoice_number_type = 3` | The external system supplies the number; CloudCart still renders and stores the document. See [[settings-invoicing-external-systems]]. |

In short, only the **number, invoice date, and Order line data** stay frozen at issue time. Everything sourced from [[settings-invoicing]] (company block, payment-method block, header rows, number formatting) is **live** on every re-render.
