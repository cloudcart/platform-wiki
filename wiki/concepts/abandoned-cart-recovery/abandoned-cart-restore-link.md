# Abandoned cart — restore link URL & click handler

## Definition

The recovery message (email or Messenger) carries a URL of the form:

```
/restore-abandoned/{code}/{source}/{discount_code?}
```

Three segments:

- **`{code}`** — a freshly-generated unique token tied to the cart at send time.
- **`{source}`** — either `email` or `messenger`; this value is what the recovered order's `restore_source` meta will be tagged with (see [[abandoned-cart-attribution]]).
- **`{discount_code}`** — OPTIONAL recovery discount code the merchant attached to entice the customer back. If set, this code auto-applies to the cart when the customer clicks the link.

The token is generated by `generateRestoreCode` per send — re-sends produce a new token each time. The token is the cart's identity for restore purposes; the platform's restore handler validates it against the cart's stored token before restoring contents.

## Scope

Covered:

- The `/restore-abandoned/{code}/{source}/{discount_code?}` URL anatomy.
- What the restore handler does on click — validation, merge-into-active-session-cart semantics, address / shipping carryover rules, attribution stamping.
- The recovery-discount-expired-by-click edge case (silent no-discount).
- The "cart not deleted on restore" detail (original cart row stays in DB).
- The new cart's own re-abandonment cycle if the customer doesn't complete checkout.

Not covered here:

- How the `{source}` value ties to the recovered order's `restore_source` and the [[orders-history]] banner — see [[abandoned-cart-attribution]].
- The channel-specific differences between email-delivered and Messenger-delivered links — see [[abandoned-cart-channels]].
- Which discount codes can be attached to the restore link — see [[marketing-discounts]].

## Contrasts

- **Token-per-send vs cart-lifetime token** — each restore-link send generates a fresh token. The cart's own `key` (session token) is a separate field used for the eligibility check on the bulk-send path. The two are not the same value.
- **Restore vs merge** — the handler is NOT a "load this cart as the active cart" operation. It MERGES the abandoned cart's contents into whatever cart the customer's session currently holds.
- **Recovery discount on the link vs cart-level discount on the cart** — the URL's `{discount_code}` is auto-applied at restore time only if it's still active at click time. If expired, the cart still restores normally with no discount and no error.

## Where it applies

### What the restore handler does on click

When the customer clicks the link, the controller:

1. **Validates the restore code** against the cart. Invalid / expired token → restore fails.
2. **Calls `mergeCart`** on the customer's currently-active session cart and the abandoned cart — items from the abandoned cart are added on top of whatever is already in the new session cart. Same-variant duplicates merge by summing quantities.
3. **Auto-applies the recovery discount code** (the URL's `{discount_code}` segment), if attached and still active.
4. **Records the recovery source** for attribution — the new active session cart is stamped with `abandoned = true` and `restore_source = email` (or `messenger`). When the customer eventually checks out, the resulting order inherits these flags (see [[abandoned-cart-attribution]]).

### Address / shipping carryover — guest vs logged-in

The customer's shipping type / shipping address / billing address / discount code attached to the abandoned cart are also re-applied to the new session cart, **but ONLY if** the abandoned cart's `user_id` matches the currently-authenticated customer.

- **Logged-in restore** — addresses + shipping type + cart-level discount carry over.
- **Guest restore** (no `user_id` match) — items merge; addresses / shipping / discount are dropped. The customer re-enters these in checkout.

This guards against leaking one customer's stored addresses to another customer who happened to receive a forwarded link.

### What does NOT happen on restore

- **The original abandoned cart row is NOT deleted.** The deletion line in the restore handler is commented out. (verify) The original cart row remains in the database. In principle it could still appear in [[orders-abandoned]] until it ages out — but once a NEW cart exists for the same customer with the merged items, the original is typically excluded by the eligibility checks (see [[abandoned-cart-eligibility]]).
- **The customer is NOT redirected to checkout-step-3 directly.** The handler restores into the active session cart and returns the customer to a normal cart / checkout flow. They can still add more items, apply more discounts, or change shipping before submitting.

### Recovery discount expired by click time

If the discount has been deactivated or expired by the time the customer clicks, the URL's `{discount_code}` lookup against the active-discount catalog returns nothing — the cart still restores normally, but **no discount auto-applies** and **no error message** surfaces to the customer. The customer simply doesn't see the discount in their restored cart.

Merchants should keep any recovery discount code's expiry comfortably beyond the recovery window. See [[marketing-discounts]] for discount-code lifecycle.

### When the customer clicks but doesn't complete checkout

The restored cart is now the customer's active cart. If they idle past the abandoned threshold (see [[abandoned-cart-threshold]]) again, the NEW cart can re-enter the abandoned pool and qualify for another round of recovery — subject to:

- Re-running the seven-check eligibility filter (see [[abandoned-cart-eligibility]]).
- Re-checking the two-layer marketing consent.
- Consuming another unit of the `abandoned_notification` plan quota (see [[abandoned-cart-plan-quota]]).

So a customer can in principle receive multiple recovery emails for the same shopping intent, one per cart-cycle, until the plan quota runs out or the customer either converts or unsubscribes.
