# Headless — legacy-vs-Nitrogen surface map

## Definition

Several customer-facing endpoints are served by CloudCart's **legacy hosted storefront only** — they do NOT auto-appear on a Nitrogen custom domain. A merchant moving to Nitrogen needs to understand which features they inherit by default and which ones their app must re-implement.

This page is the **gap map**: for each affected surface, it documents what the legacy storefront does and what a Nitrogen storefront must do instead.

## Scope

Covered:

- `/robots.txt` and `/sitemap.xml` generation.
- 301 redirect rules from [[marketing-seo-301-redirects]].
- The trial / `plan_expired` `Disallow: /` SEO override.
- Cart-bubble JavaScript + payment-provider redirect pages + hosted `/orders/<id>` confirmation.
- Multi-domain language storefronts.

Not covered:

- General SEO mechanics (canonical URLs, metadata) — see [[seo-handling]].
- The legacy storefront's internal Smarty templating — not relevant to merchants choosing Nitrogen.
- The CloudCart admin (same admin regardless of storefront kind).

## Contrasts

- **Legacy storefront serves these by default** — robots.txt, sitemap.xml, 301 redirects, plan-expired SEO override, cart-bubble JS, payment redirect pages, hosted order-confirmation, per-domain language pinning. Merchant gets them for free on legacy themes.
- **Nitrogen storefront serves NONE of these by default** — the merchant's app must implement equivalents OR fall back to hosted CloudCart URLs for specific legs.

## Where it applies

### `/robots.txt` and `/sitemap.xml`

Both are generated by the **legacy storefront**. The Nitrogen custom domain has NO equivalent built-in handler — the merchant's Nitrogen app must serve its own `robots.txt` and `sitemap.xml`.

Typical Nitrogen pattern: generate `sitemap.xml` at build time from the `/api/sf` GraphQL API (products, collections, content pages) and ship a static `robots.txt`.

If the merchant points their primary domain at Nitrogen but leaves the legacy storefront live on a secondary domain, the legacy storefront still serves robots/sitemap on the secondary — but search engines crawl what's on the primary. So a merchant who skips the in-app robots/sitemap effectively loses SEO until they ship them.

### 301 redirect rules

The redirect rules the merchant configures on [[marketing-seo-301-redirects]] apply ONLY to legacy-storefront URLs. Nitrogen storefronts do NOT automatically pick them up.

Nitrogen merchants implement their own redirect layer:

- **Cloudflare Page Rules** on the custom domain (fastest, no app code).
- **In-app middleware** (Next.js `redirects` config, Remix loader 302s, etc.).
- **Worker-level redirect logic** in the deployed app's request handler.

A common migration pattern: export the legacy redirect rules from [[marketing-seo-301-redirects]], then re-create them via Cloudflare Page Rules or feed them into the Nitrogen app's redirect config at build time.

### Plan-expired / trial `Disallow: /` SEO override

When a merchant's plan expires or they're in trial, the legacy storefront's robots-handler overrides robots.txt to `Disallow: /` — blocking search engines from indexing the storefront. See [[seo-handling]] for the full mechanics.

This override does NOT propagate to Nitrogen domains automatically. A Nitrogen merchant whose plan expires keeps serving their own `robots.txt` as configured. If they want crawlers blocked during a paused subscription, they must:

- Add the `Disallow: /` rule themselves in their Nitrogen app's robots.txt, OR
- Query the merchant's plan state from the Storefront API at request time and adjust their robots-handler accordingly.

CloudCart's admin still treats the storefront as plan-expired (admin UI restrictions still apply — see [[plan-gates]]) but the customer-facing storefront keeps serving whatever the Nitrogen app outputs.

### Cart-bubble JavaScript, payment-provider redirect pages, hosted `/orders/<id>` confirmation

These are legacy-storefront features:

- **Cart-bubble JS** — the floating cart widget that updates as the customer adds products. Nitrogen apps either re-implement it or skip it entirely (modern frontend frameworks typically render this from app state).
- **Payment-provider redirect pages** — the intermediate page the customer hits when redirected from a payment provider (Stripe, PayPal, ePay, etc.) back to the merchant's domain before being bounced to the final confirmation page. The legacy storefront serves this at known URLs.
- **Hosted `/orders/<id>` confirmation page** — the order-thank-you page customers see after a successful payment, rendered by the legacy storefront's templates.

Nitrogen merchants have TWO options for each:

1. **Re-implement in the Nitrogen app** — full control of the UX but more work.
2. **Fall back to the hosted CloudCart URL** — the merchant configures the payment provider to return to a hosted CloudCart URL (e.g., the legacy storefront's payment-return endpoint), the legacy storefront processes the redirect, and then the storefront either renders the confirmation page or bounces the customer back to the Nitrogen domain.

The fallback pattern is especially common for the payment-provider redirect leg, because the payment provider's return URL is locked at provider-config time and merchants don't want to redirect-juggle on a domain Cloudflare doesn't manage.

### Multi-domain language storefronts

The legacy storefront supports **per-domain language pinning** out of the box — a merchant with `example.de` + `example.com` + `example.fr` gets German / English / French content served per domain automatically. See [[multi-language]] for the legacy mechanics.

On Nitrogen, the routing pattern depends **entirely** on the merchant's app implementation. Common patterns:

- One Nitrogen storefront per language, each with its own Nova hostname + custom domain (uses up one slot per language toward the per-site cap — see [[headless-nitrogen-overview]]).
- A single Nitrogen storefront with locale-based routing inside the app (`/en/...`, `/de/...`) and the Storefront API queried with a locale parameter.
- A single Nitrogen storefront with subdomain routing (Worker reads `request.url.hostname`, switches locale in-app).

There is NO platform-level "per domain → per language" wiring for Nitrogen; the merchant's app owns this entirely.

### Quick reference table

| Surface | Legacy serves it? | Nitrogen serves it by default? | What Nitrogen merchant must do |
|---|---|---|---|
| `/robots.txt` | Yes | No | Ship a static `robots.txt` from the app |
| `/sitemap.xml` | Yes | No | Generate at build time from `/api/sf` |
| 301 redirect rules ([[marketing-seo-301-redirects]]) | Yes | No | Cloudflare Page Rules OR in-app middleware |
| `Disallow: /` on plan expiry | Yes (auto) | No | Query plan state, output own robots.txt rule |
| Cart-bubble JS | Yes | No | Re-implement in app |
| Payment-provider redirect page | Yes | No | Re-implement OR use hosted fallback URL |
| Hosted `/orders/<id>` confirmation | Yes | No | Re-implement OR use hosted fallback URL |
| Per-domain language pinning | Yes | No | App-level locale routing |
