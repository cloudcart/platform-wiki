# Settle

## Purpose

Settle Group is a Lithuanian/EU payment-and-banking platform offering card processing and an e-commerce gateway. It accepts Visa, Mastercard, and locally-relevant methods for the EU market. The integration uses an **RSA-signed JSON API** with custom `x-settle-*` headers — a more enterprise-style integration than typical hosted-gateway flows.

Settle suits **EU stores wanting a Lithuanian-licensed provider** with strong B2B features. It is less common than Stripe/Mollie but useful where regional regulatory alignment matters (Lithuanian or Baltic business stores). API endpoints are `api.settle.eu` (live) and `api.sandbox.settle.eu` (test) — the `.eu` TLD signals pan-EU positioning rather than Lithuania-only.

## Where to find it

Payment Providers → **Settle**. URL: `/admin/payment-providers/settle`. Route name: `apps.settle.settings`. Renders the standard Settle edit form.

## What the merchant can do here

- Toggle the provider **Active**.
- Switch between **Test mode** and **Live mode** with the Test mode switch. Help text: "Use test mode to test your connection. Live mode is for the actual payment processing. Use live mode when you have verified your credentials."
- Enter the **X-Settle-Merchant** identifier — given by Settle when you create an API key.
- Enter the **X-Settle-User** identifier — given by Settle when you create an API key.
- Paste the **Secret RSA Key** — the private RSA key used to sign API requests, generated by Settle's onboarding flow.
- Configure storefront name, logo, accepted-amount range, and an optional discount when paying with Settle.

## Settings & fields

The route shows the standard header/tabs/logo/environment-mode block, then one Settle-specific card (key `configuration`, always visible, border color follows mode), the common Amount-from/to + Discount rows, and a sticky submit bar. `configurationDefault.settle = { mode: 'test', discount_type: 'flat' }`.

## Business rules

### Customer flow at checkout

1. Customer picks Settle at checkout; CloudCart creates a payment row.
2. CloudCart builds a new-sale payment request (amount in minor units, currency, site ID, order ID, plus success/failure return URIs and the callback/webhook URI) and calls Settle's payment-request API. The request is RSA-signed with the merchant's private key.
3. Settle returns a payment record with a `uri` (redirect URL) and an `id`. CloudCart stores the `id` as the provider reference. Payment status → `requested`.
4. Customer is redirected to Settle's hosted payment page, enters card details, and completes payment.
5. Settle redirects to CloudCart's `payments.return` URL and POSTs an IPN to the `payments.webhook` URL with the latest status.

### Two-step flow: auth → capture (handled internally)

When CloudCart's complete-purchase / sync handler runs, it calls Settle's check-transaction-status API; if the returned status is `AUTH` (authorized but not captured), CloudCart **automatically calls capture** with the stored reference, then re-fetches the status to confirm.

So from a merchant perspective Settle behaves like **auto-capture**, even though the API performs two distinct steps server-side. There is no way to keep an authorization "held" through the CloudCart flow — capture is always invoked, and there is no manual-authorize-only mode. Merchants who genuinely need to hold authorizations (e.g. pre-orders that may be cancelled before shipping) should use a provider with an explicit Manual capture mode such as [[payment-providers-monri|Monri]], [[payment-providers-raiffeisen|Raiffeisen]], [[payment-providers-dsk-bank|DSK Bank]], or [[payment-providers-btepos|BT ePOS]].

### Status mapping

Settle returns `FAIL`, `PENDING`, `AUTH`, `OK`, which map to platform payment statuses:

- `OK` → `completed`
- `PENDING`, `AUTH` (before capture) → `pending`
- `FAIL` → `failed`
- Any entries in `response.refunds` → `refunded` (regardless of `status`)

### Refunds

Supported. CloudCart calls Settle's refund endpoint with the saved payment ID and a description "Refund Order #{order_id}". On HTTP 200 or 204, the payment status flips to `refunded`. Partial refunds are not exposed in the UI.

### RSA signing — every API request

Every request is signed with the merchant's private RSA key (algorithm **RSA-SHA256**); Settle validates it against the merchant's registered public key. The request body is SHA256-digested into the `x-settle-content-digest` header, the signature is attached to the `Authorization` header as `RSA-SHA256 <base64-signature>`, and a UTC timestamp is sent on `x-settle-timestamp` (with `x-settle-merchant` and `x-settle-user`).

This asymmetric scheme is stronger than HMAC shared-secret signing: an attacker who steals the merchant code and user **cannot** make API calls without also stealing the private key, and Settle can cryptographically prove which merchant initiated each call. The private key never leaves CloudCart's database.

### Currency

CloudCart sends the order's native currency; the merchant's Settle contract determines which currencies are accepted (typically EUR, USD, GBP, BGN, RON, PLN, etc.).

### Other behaviour

- **3D Secure** — handled by Settle on their hosted page when the card requires it.
- **Sandbox / test mode** — in test mode the client targets Settle's sandbox endpoint; test cards and credentials come from Settle onboarding.
- **Recurring / subscriptions** and **saved cards / tokenization** — not implemented in this integration.
- **Plan-gating** — none.
- **Permission** — requires the standard payment-providers permission (`store.payment_providers`).
