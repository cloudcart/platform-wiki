# Web Push channel — Subscription flow

## Purpose

This aspect documents what happens **after** the customer clicks **ALLOW** on the CloudCart popup and grants the native browser permission. The browser issues a per-device subscription, the storefront POSTs it to `/web-push-subscribe`, and CloudCart creates or updates a Subscriber with a WebPush `SubscriberChannel` row that holds the endpoint URL and the encryption keys needed to send to that device.

The Web Push subscription identifier is **not** an email or phone number — it is a tuple of `endpoint` (the push-service URL the browser issued), `keys.p256dh` (the ECDH public key the device generated), and `keys.auth` (the auth secret). Without all three, sends are impossible.

## Where to find it

The storefront-side flow is invisible to the merchant — handled by the storefront's service worker driven by the [[webpush-channel-storefront-prompt|popup settings]]. The merchant sees the result on **Marketing → Subscribers** ([[marketing-subscribers]]), where each subscriber's **WebPush** channel row shows the `channel_identifier` (a hash of the endpoint URL).

The subscribe endpoint is the storefront route `/web-push-subscribe` (route name `campaigns.channels.channel.web_push.subscribe`). It does NOT require login.

## What the merchant can do here

There is no merchant action on this flow — it runs autonomously between the customer's browser and the storefront. Downstream, the merchant can:

- View resulting subscribers on [[marketing-subscribers]] — filter by WebPush channel installed.
- Target the resulting subscribers in a campaign step of type **Web push notification** (`web_push`) — see [[webpush-channel-send-pipeline]].

## Settings & fields

### Storefront POST payload — `/web-push-subscribe`

The storefront JS POSTs:

| Field | Source | Required? |
|---|---|---|
| `endpoint` | Browser-issued push-service URL (FCM / Mozilla Autopush / WebPush gateway) | Yes |
| `keys.p256dh` | Base64url-encoded ECDH public key generated by the device | Yes |
| `keys.auth` | Base64url-encoded auth secret generated by the device | Yes |
| `uuid` (cookie or input) | Subscriber correlation cookie | Optional — falls back to authenticated customer / cart's `subscriber_id` |

If any of `endpoint`, `p256dh`, `auth` is missing, the endpoint silently returns `{status: success}` (the storefront cannot differentiate). This is intentional — Web Push subscription is best-effort, and the storefront cannot debug what the browser did or didn't return.

### `SubscriberChannel.data` JSON — what gets stored

```
{
  "endpoint": "https://fcm.googleapis.com/wp/...",
  "keys": {
    "p256dh": "<base64url-encoded ECDH public key>",
    "auth": "<base64url-encoded auth secret>"
  }
}
```

The `channel_identifier` column on the WebPush channel row is **an MD5 hash of the endpoint URL** — used for matching the recipient on subsequent subscribes (so the same browser doesn't create duplicate Subscriber rows). The full subscription payload above lives in `data`.

### `_cc_wp` storefront cookie

| Cookie | Lifetime | Purpose |
|---|---|---|
| `_cc_wp = 1` | 86400 seconds (24 hours) | Set on successful subscribe. The storefront uses this to suppress the [[webpush-channel-storefront-prompt|popup]] for already-subscribed visitors during that window. |

## Business rules

### Subscribe creates OR updates — never duplicates

The handler hashes the endpoint URL with MD5 to derive the `channel_identifier`, then:

1. Looks up the existing Subscriber via cookies (`uuid` cookie, request input, or cart's `subscriber_id`) OR by the authenticated customer.
2. Calls `saveSubscriberByChannels` with the **`FROM_WEB_PUSH`** source flag.
3. Creates or updates the matching subscriber + their WebPush channel row with `marketing = 1`. `verified` is implicit — the act of subscribing IS verification (the browser only issues an endpoint after explicit user consent, so no second-step email/SMS verification is needed).

If a different browser on the same device subscribes again, the endpoint will differ — a new WebPush row is created. Two browsers = two WebPush channel rows on the same subscriber.

### `verified = 1` is implicit — no double opt-in

Unlike Email / SMS / Viber, the WebPush channel does **not** track a separate `verified` flag the merchant can toggle. The native browser permission prompt IS the verification gate. This also means there is no `unconfirmed_send` setting for Web Push (compare [[email-channel-settings-pane]]).

### Logged-in customers — implicit Email-channel link

If the customer is logged in at the moment they accept the prompt AND the [[marketing-channels-email|Email channel]] is installed on the store, the subscribe handler ALSO links the subscriber to their Email channel using the platform code and the customer's full name. This is the **"all-channel onboarding"** flow some merchants rely on: a single WebPush opt-in implicitly creates the Email channel record too.

### Geo-IP and User-Agent recorded on subscribe

The subscribe endpoint captures the platform code (geo-IP lookup) and the User-Agent header, attaching both to the new SubscriberChannel row. The merchant does not see these directly, but **segment conditions can filter on them** when targeting a campaign — e.g. "Web Push subscribers from Bulgaria using Chrome on Android".

### Subscribe is best-effort — silent success on partial payloads

The endpoint returns `{status: success}` whether or not the subscriber row was actually created. The storefront cannot detect failure. This is by design — the merchant cannot meaningfully recover from "browser didn't return p256dh" on the client side, and exposing the error would only invite log-noise / support tickets.

### Race with logout/login

A subscriber who is unauth at subscribe time and later logs in does NOT automatically inherit the WebPush subscription onto their customer record unless they re-trigger the subscribe flow. The current handler correlates via the `uuid` cookie at subscribe time only — the merging happens elsewhere in the subscriber-stitching pipeline (verify).
