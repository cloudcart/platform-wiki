# Two-factor authentication

## Purpose

The **Two-factor authentication (2FA)** screen lets the admin secure their CloudCart login with a second factor — a **TOTP** (time-based one-time password) generated by an authenticator app on their phone. Once enabled, every sign-in requires both the password AND the current 6-digit code, making the account significantly harder to compromise.

Recommended for any admin handling orders, customer data, or financial information; critical for stores in regulated markets (GDPR / N-18 audit). Supported apps: **Google Authenticator, 1Password, Authy, Microsoft Authenticator** (any RFC 6238 TOTP app). An **email-based fallback** ([[account-cc2fa-email]]) delivers the code by email when the merchant can't set up an authenticator app.

## Where to find it

Sidebar → Profile (top-right user menu) → **Two-factor authentication**, OR direct route `/admin/account/cc2fa`. Breadcrumb reads "Profile → Two-factor authentication". The backup-codes sub-page is at `/admin/account/cc2fa/codes`.

## What the merchant can do here

### Setup (when 2FA is NOT yet enabled)

Header: **"Setup two-factor authenticator app"**. Help text: *"Authenticator apps like Google Authenticator, 1Password, Authy, Microsoft Authenticator, etc. generate one-time passwords as a second factor to verify your identity when prompted during sign-in."*

- **STEP 1 — Scan the QR code.** The QR (an `otpauth` URI) is displayed. Help: *"Use an authenticator app or browser extension to scan."* Link *"Learn more about enabling 2FA"* → `https://help.cloudcart.com/en/support/solutions/articles/77000557211-two-factor-authentication/`.
  - **Alternative — Show setup key.** A toggle displays the secret as plain text instead of the QR — useful when configuring on the same device that has the authenticator (no camera).
- **STEP 2 — Enter verification code.** The merchant types the current 6-digit code to confirm setup works.
- **STEP 3 — Save backup codes.** On success the platform mints **one-time-use backup codes** ([[account-cc2fa-codes]]) to download/print for when the authenticator is lost.

### After 2FA is enabled

- The page shows current 2FA status.
- **View / regenerate backup codes** → [[account-cc2fa-codes]].
- **Disable 2FA** — typically requires re-entering the password + a current code.

### Email-based 2FA

Alternative flow via [[account-cc2fa-email]] at `/admin/account/cc2fa-email` for merchants without an authenticator. The route `admin.account.cc2fa-email.send` (GET `/account/cc2fa-email/send`) triggers a code to the admin's email.

### What the merchant CANNOT do here

- Enable 2FA without first scanning the QR / entering the secret into an authenticator.
- Recover the account if BOTH the authenticator and backup codes are lost — they must contact CloudCart support.
- Force 2FA on OTHER admins — 2FA is per-admin self-service (admin management is in [[settings-staff]]).

## Settings & fields

### QR setup card

- `data.otpauth` — URI encoded in the QR (`otpauth://totp/CloudCart:<email>?secret=<key>&issuer=CloudCart`).
- `data.secret` — the secret key as plain text (alternative to scanning).
- `displaySetupKey` toggle — switches between QR and plain-text secret.

### Layout

- **Desktop (> 768px)** — QR rendered at 200×200 px with `level="H"` (most error-correcting).
- **Mobile** — alternative narrow-screen layout.

### Platform config defaults

| Setting | Value | Meaning |
|---|---|---|
| `OTP_ENABLED` | `true` | Master switch (env). |
| `OTP_LIFETIME` | `0` (eternal) | 2FA-verified session validity; 0 = no expiry. |
| `OTP_KEEP_ALIVE` | `true` | Refreshes lifetime on every request. |
| `keySize` | `16` | TOTP secret length (characters). |
| `window` | `1` | Time-skew tolerance: ±1 × 30s. |
| `forbid_old_passwords` | `false` | The same OTP CAN be reused within its window. |
| `otp_secret_column` | `cc2fa_secret` | Column storing the secret. |
| `qrcode_image_backend` | SVG | QR rendering format. |
| `guard` | `admin` | 2FA applies to the admin guard only (not customers). |
| `session_var` | `cc2fa` | Session-var name for verified state. |
| `otp_input` | `one_time_password` | Request input name. |

## Business rules

### TOTP standard

6-digit codes, refreshed every 30 seconds, per RFC 6238. The `window = 1` setting accepts the **current**, **previous**, and **next** 30-second code — total acceptance window ≈ 90 seconds, generous for clock skew.

### Same code can be reused (`forbid_old_passwords = false`)

The same OTP can be re-submitted within its valid window. This prevents the "submitted twice" UX bug but slightly weakens security; some merchants may want it hardened.

### Login-time only (eternal verified session)

`OTP_LIFETIME = 0` + `OTP_KEEP_ALIVE = true` mean the merchant verifies 2FA **once at login and stays verified until the session ends or they explicitly log out** — never re-prompted per-request or per-day. This applies to both TOTP and the email fallback. Efficient for usability, but an attacker who steals an active session bypasses 2FA.

### One-time backup codes

Generated on successful setup; each code works ONCE, then is invalidated. The pool is replenished to **12 unused codes** every time the merchant opens the codes page, so using some codes is topped back up on the next view. Used codes are retained internally but hidden; the merchant sees only the 12 unused ones. Details on [[account-cc2fa-codes]].

### Email fallback is lower-security

Email-delivered codes are valid for a short window (5–15 minutes). Email 2FA is weaker than TOTP — if the mailbox is compromised, so is the 2FA.

### Per-admin self-service

Each admin enables 2FA for their own account. There is no store-wide "force 2FA for all admins" toggle; the store owner cannot force-enable it on other staff from this page — see [[settings-staff]].

### Lost-access recovery

If both the authenticator and backup codes are lost: (1) use the email-based fallback if set up; (2) otherwise contact CloudCart support, who can disable 2FA after identity verification.

## The 2FA prompt at login

After entering email + password on `/admin/login`, an admin with 2FA enabled (or platform-level email 2FA on) is sent to the **2FA challenge page**. What the merchant sees:

- Header *"Configuration access requires verification"*, their avatar, *"Signed in as `<email>`"*, and an **Exit** link → `/admin/logout`.
- One **6-digit code input** (`name="one_time_password"`) + a **Validate** button.
- A **"Use a restore code instead"** link that flips to a single **backup-code input** (`name="code"`), with a link to swap back.

The backup-code path checks the code exists for that admin and is unused; errors are explicit — *"This restore code does not exist"* or *"That restore code is already used"*. On success the code is marked used, the verified session is granted, and the merchant lands on their dashboard.

During initial **setup** (not login), entering the code in STEP 2 and clicking **Validate** (or Enter) verifies it against the pending secret. If valid and the admin had no secret yet, the secret is saved, the first 12 backup codes are minted, and the page advances to the codes view. Invalid → inline *"The 'One Time Password' typed was wrong."*; empty → *"One Time Password cannot be empty."*
