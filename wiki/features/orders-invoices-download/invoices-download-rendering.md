# Invoices bulk download — PDF rendering

> Part of [[orders-invoices-download]]. See the hub for related aspects (entry point, scope, sync/async, permissions/plan).

## Purpose

Documents how each PDF in the bundle is produced: rendered fresh from current order data (not pulled from an archive), named by invoice number, watermarked per the Bulgarian-locale rules, and which documents are excluded. Also covers the global-invoicing short-circuit. This behaviour is unchanged by the redesigned Invoices list.

## Where to find it

Rendering happens server-side when the merchant triggers a download from the **Download** button on [[orders-invoices]] (see [[invoices-download-entry-points]]). The output template is the store's currently-configured invoice template, set on [[settings-invoicing]].

## What the merchant can do here

- Get a ZIP whose contents match the single-invoice download in [[orders-invoice]] — the same PDF generator is used, so output is consistent between flows.

### What the merchant CANNOT do here

- Customise the layout from this action — the bundle uses the store's currently-configured invoice template.
- Get credit-note PDFs in the bundle — credit notes are a separate flow (see Business rules and [[orders-credit]]).
- Get a meaningful bundle while invoicing is globally disabled — every PDF short-circuits to empty (see Business rules).

## Settings & fields

### Filename pattern

- The bundle archive (synchronous): `invoices-YYYY-MM-DD-HH-MM-SS.zip` (see [[invoices-download-sync-async]]).
- Each invoice inside the archive: `Invoice-<formatted_invoice_number>.pdf`, where the formatting uses the store's configured invoice-number format (prefix + padding + numeric series — see [[settings-invoicing]]).

## Business rules

### PDFs generated on demand — not stored

Each invoice PDF is generated FRESH at download time from the order's current data, NOT pulled from a pre-rendered archive. This means:

- The PDF reflects the order's current state (e.g., if line items changed since the original invoice).
- Re-downloading the same invoice number can produce a different PDF if the underlying order has been edited.
- The invoice NUMBER and DATE are locked once assigned — but the rendered content is recomputed.

This is intentional — invoices are always current snapshots: whatever the order looks like now is what renders. Note that **line items can no longer be edited once the order is invoiced** (fiscal rule — see [[orders-details-products]]), so in practice the drift comes from the surfaces that remain editable after invoicing (e.g. address or tax-setting changes), not from quantity / price edits.

### Per-invoice rendering matches the single-invoice flow

The bundle iterates the matched orders and uses the same invoice generator as [[orders-invoice]] — the merchant gets identical output between single-download and bulk-download flows.

### Per-PDF watermark behaviour identical to single-invoice flow

Each PDF in the bundle goes through the same Bulgarian-locale watermark check as the single-invoice flow ([[orders-invoice]]). So a bundle containing a mix of paid + cancelled orders for a BG-language store will have *"Original"* watermarks on paid invoices and *"Voided"* (or the configured override) on cancelled ones.

### Credit notes are NOT included in the bundle

The bundle only contains invoice PDFs. Credit notes (refund documents) are generated by a separate flow and are NOT bundled into this archive. For credit-note PDFs, the merchant uses the per-order credit-note download from [[orders-credit]].

### `invoicing = no` short-circuits every PDF in the bundle

If the merchant disabled invoicing globally between assigning numbers and downloading the bundle, invoice generation returns empty for every order. The bundle is still produced but each entry would be empty/invalid. There is no pre-flight check on the bundle path — the merchant should verify [[settings-invoicing]] is enabled before bulk-downloading.

### Template changes affect re-rendered historical invoices

Because rendering uses the store's currently-configured invoice template at download time, a template change DOES affect re-rendered historical invoices.
