# Facebook Pixel + CAPI → Settings

## Purpose

The **Settings** tab is where the merchant enters the **Pixel ID** + **Access Token** + **Test Event Code** and toggles the server-side **Conversions API (CAPI)** on/off. See [[apps-facebook-pixel]] for the full feature set.

## Where to find it

Sidebar → Apps → XML Feed → Facebook → **Settings tab**. Route: `/admin/apps/xml_feed/facebook/settings`.

## What the merchant can do here

### Configuration

The Settings UI exposes these fields for the Pixel + CAPI half of the integration:

| Field | Stored as | Notes |
|---|---|---|
| **Facebook Pixel ID** | `pixel` | Numeric only — e.g. `432543676657523`. Placeholder advises **NOT** to paste the full Pixel JS snippet, only the numeric ID. |
| **Access Token** | `token` | Long-lived system-user token generated in Meta Events Manager → Settings → Conversions API. Required for CAPI. |
| **Test Event Code** | `test_event_code` | Optional — pastes the temporary code from Meta Events Manager → Test Events. When set, CAPI events get tagged with this code so they surface in the Test Events panel. Leave empty in production so real events are not filtered out. |
| **Enable CAPI** | `capi_status` | Switch (1/0). Activates the server-side path. |

The same Settings page ALSO carries the **product catalog feed** configuration (currency, category mapping, included-products filter) — see [[apps-xml-feed]] for those fields. The two halves (Pixel/CAPI tracking + catalog feed) live in the same page because they share the app key `app.xml_feed.facebook`.

### Privacy / consent integration

When [[apps-gdpr-overview]] is active and the visitor rejects the **Targeting** cookie group, NEITHER the browser pixel NOR the server-side CAPI fires. The merchant doesn't configure granular per-event consent — it's a single all-or-nothing gate tied to the `targeting` cookie group.

### What the merchant CANNOT do here

- View Pixel analytics inside CloudCart — go to Meta Events Manager.
- Use without a Meta Business account + Pixel created in Events Manager.
- Per-event toggles — events fire automatically per the standard vocabulary.
- Add custom events.

## Settings & fields

App key: `app.xml_feed.facebook`. Same Manager as the product catalog feed half.

## Business rules

### Plan gate

CAPI requires the `facebook.capi` plan feature. Merchants on plans without it can fill the form, but the server-side CAPI path is short-circuited (only the browser pixel fires). The UI surfaces the plan-meter warning when the plan feature is missing.

### Access Token

Long-lived system-user token, generated by the merchant in Meta Events Manager → Settings → Conversions API → Generate Access Token. CloudCart does not refresh the token automatically — if Meta invalidates it, the merchant has to regenerate and paste in. Token failure logs as `Facebook CAPI error` in the router logs and silently degrades to browser-pixel-only.

### Test Event Code workflow

1. Merchant opens Meta Events Manager → Test Events.
2. Copies the displayed test event code (changes per session).
3. Pastes into the **Test Event Code** field here and saves.
4. Triggers events on the storefront — they appear within ~5s in Meta's Test Events panel tagged with the code.
5. Once verified, the merchant clears the field so production events aren't filtered.

### Cookie consent gating — Targeting group

Both the browser-pixel and server-side CAPI paths check whether the visitor accepted the `targeting` cookie group. See [[apps-gdpr-cookies]]. No partial fire — it's all-or-nothing.

### One Pixel ID per store

Only one Pixel ID per store install. For multi-pixel routing the merchant has to use [[apps-google-tags]] (GTM) and disable CAPI here.

### Permission

Standard apps permission scope. Plan-gated by `facebook.capi`.

## How it works (verified against backend)

### Settings whitelist — these are the exact saved fields

Only `pixel`, `token`, `test_event_code`, and `capi_status` are read by the CAPI controller from the merchant's saved settings. Additional fields in the form (catalog-feed currency, mapping, filter — see [[apps-xml-feed]]) are persisted but consumed by the feed generator, not the CAPI path.

### CAPI fires only when ALL of these are true

1. Plan: `facebook.capi` feature enabled.
2. Settings: `token` is non-empty AND `capi_status` = 1.
3. Consent: visitor accepted the `targeting` cookie group.
4. Request: storefront sent a valid `_token` CSRF in the AJAX body, and the request carries a non-empty `data.eventID` + `data.external_id`.
5. Auth: the request is NOT from an authenticated admin user (admins are excluded so admin previews don't fire conversion events).

If any gate fails, only the browser pixel fires (and the browser pixel itself is gated by the Targeting cookie group).

### Test Event Code routing

When `test_event_code` is set on the Manager, every CAPI request adds the code via the platform code before execution. This tags every event with the test code regardless of which event type fires — there's no per-event-type test mode.

### Event source URL — known critical gap (BUG, 2026-06-08)

See [[apps-facebook-pixel]] → "Known issues — `event_source_url`" for full details. Short version: `event_source_url` is sent only for `PageView`, `ViewContent`, `InitiateCheckout`, and `Purchase` (the last two with a relative path, not absolute URL). `AddToCart`, `AddToWishlist`, and `Search` send NO URL. Meta has warned this will cause event blocking in ~3 days. Engineering fix pending; merchant cannot work around from this Settings page.

### Errors never surface to the storefront

CAPI failures (timeout, 5xx from Meta, invalid token, malformed payload) get caught and logged as `Facebook CAPI error` into the router logs entity. The storefront page renders normally, the user sees nothing wrong, and no retry is queued. So degraded CAPI is invisible to the merchant until they check Meta Events Manager → Diagnostics.
