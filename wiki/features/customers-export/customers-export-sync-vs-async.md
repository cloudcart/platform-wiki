# Export customers — sync vs async

## Purpose

This aspect covers **what happens after the 2FA code is accepted**: whether the file is returned immediately in the response or generated by a background job. The deciding factor is the number of customers in the filtered set, compared against a fixed synchronous-row threshold.

## Where to find it

There is no UI for this choice — the platform picks the path automatically based on the matching customer count. The queued job does not appear on the **Queue jobs** page; its result arrives as described below.

## What the merchant can do here

### Small dataset → immediate file

- Under the threshold (default **5 000** rows), the CSV is returned in the same HTTP response and the browser downloads it directly.
- The Export button shows a spinner while the file is being prepared.

### Large dataset → background job

- Over the threshold, the export is enqueued as a background **CustomerExport** job (with a default chunk size of **10 000** rows per batch).
- The merchant gets a `queue` response and the toast *"The export is being processed. You will receive an email with the download link."* When the job finishes, the file appears in **Settings → Files** ([[settings-files]], archive folder), an email with the download link goes to the store's email address ([[settings-admin-notifications]]), and an admin notification says the download is ready, linking to the file and to Files.

### What the merchant CANNOT do here

- Force synchronous mode for a large export — the threshold decides automatically.
- Override the row limit or chunk size from the UI — they are configured per-task.

## Settings & fields

### Synchronous vs queued thresholds

| Setting | Default | Notes |
|---------|---------|-------|
| **Synchronous row limit** | 5 000 | At or below this, the CSV is returned in the response. |
| **Queue chunk size** | 10 000 | Background job processes this many rows per part file. |

These thresholds are configured per-task; the merchant cannot override them from the UI.

### Response shapes

When the matching customer count is at or below the synchronous limit:

```
{ "status": "success", "type": "csv", "filename": "customers-YYYY-MM-DD-HH-MM-SS.csv", "data": [...rows...] }
```

When the count exceeds the limit:

```
{ "status": "success", "type": "queue", "filename": null, "data": [] }
```

The merchant's browser handles the response: `csv` triggers an immediate download; `queue` shows the toast above.

## Business rules

### How the path is chosen

The trait inspects the customer count under the current filter set (see [[customers-export-filter-scope]]). If the count is at or below `limit` (defaults to 5 000), it builds the CSV directly and serialises the rows to the response. Otherwise it enqueues a `generate_by_sql` job of type `CustomerExport` (on the `export6` queue), passing the SQL representation of the filtered query and a per-batch chunk size (default 10 000).

### Large exports arrive as multiple part files

When the export exceeds the synchronous limit, the platform:

1. Re-runs the snapshot SQL with a `COUNT(*)` to get the true total.
2. Splits the result into pages of `chunk` rows each (default 10 000).
3. Dispatches one delivery job per page, naming each file `customers-YYYY-MM-DD-HH-MM-part_N.csv`.
4. Each delivery job re-queries its page slice, streams rows to a CSV (250 rows per query chunk) and prepends the UTF-8 BOM (see [[customers-export-csv-schema]]).
5. When all parts are done they are packed into **one ZIP** `customers-YYYY-MM-DD-HH-MM-SS.zip`, saved in the File manager, and the separate part files are removed; then the email and the admin notification go out.

So a 60 000-customer export is one ZIP holding **six** CSVs (`part_1` … `part_6`); to get a single sheet the merchant combines them. There is no overall row cap and no time limit on the job.

### SQL snapshot consistency

The background path snapshots the filtered SQL query once, so all part files are sliced from the same consistent query — customers added or removed after the job starts do not shift rows between part files.
