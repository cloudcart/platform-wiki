# AdScout

## Purpose

**AdScout** integration — exports the merchant's product catalog to AdScout (a price-comparison / advertising platform). AdScout aggregates product listings from multiple merchants and shows them to shoppers; clicks back to the merchant generate paid traffic.

The integration sits in the Exports namespace (the platform code) — pushes product data to AdScout via its API rather than via URL-pull feeds.

App key: `app.xml_feed.ad_scout` — namespaced under xml_feed family but distinct from the URL-pull [[apps-xml-feed]] integration.

## Where to find it

Sidebar → Apps → install → **AdScout**.

## What the merchant can do here

- Configure AdScout API credentials.
- Validate credentials (`isValidCredentials`).
- Activate to push products to AdScout.

### What the merchant CANNOT do here
- Use without an active AdScout merchant account.

## Settings & fields

Manager exposes:
- `appInfo` — App Store metadata.
- `isValidCredentials` — validity check.
- `getClient($apiKey)` — instantiates the AdScout API client.
- `getCredentialsFields` — returns the fields the merchant must fill in.
- `supportsCredentials: bool` — true (credential-based, not OAuth).
- `validateCredentials(?array $parameters)` — runs validation with optional parameter override.

## Business rules

### API-based push (not URL-pull)

Unlike [[apps-xml-feed]] which exposes a URL for the consumer to pull, AdScout uses an API push — the platform sends product data directly to AdScout. Better for real-time updates.

### Credentials-based

Standard credential authentication (not OAuth). The merchant pastes the API key from AdScout's portal.

### Permission

Standard apps permission scope.

## How it works (verified against backend)

### App key uses nested key pattern

The app key is `app.xml_feed.ad_scout` — a DOT-NAMESPACED key (rare in CloudCart). This indicates AdScout is a SUB-app inside the XML Feed namespace, not a standalone app.

### 2 required credentials

The required credentials are `api_key` and `domain_code`:
- `api_key` — AdScout API authentication.
- `domain_code` — identifies the merchant's domain/account.

### Credentials are validated against the AdScout API

When the merchant saves credentials, the integration calls AdScout's validation endpoint with the api_key. Any exception (bad credentials, network error, AdScout downtime) results in a "not valid" verdict — defensive by design.

### Credentials auth (no OAuth)

Credentials-based auth — no OAuth roundtrip needed for AdScout.

### Coverage region: adscout.io (single endpoint, no regional split)

The integration uses a single hard-coded base URL (`https://adscout.io/api/`). AdScout's own coverage (which markets accept the merchant's catalog) is a question for the AdScout merchant account, not the CloudCart side — the integration is region-agnostic at the platform level.

### Click attribution: cookie-based, sent back with each tracked order

When a shopper lands on the storefront via an AdScout-sourced click, AdScout sets the `AdScoutAdsRef` cookie. On order creation, the platform reads that cookie and dispatches an order-send event with the cookie value as `adsRef`. AdScout's `track-order` endpoint correlates the order to the originating click via this reference. The cookie is unset after the dispatch.

Subsequent order-status-change and fulfillment-add / fulfillment-remove events also send an order-update (type 2) so AdScout's commission/refund tracking stays in sync.

### Selective export: filtered by the XML Feed AdScout sub-feed settings

The product CSV that feeds AdScout is generated by the XML Feed module's AdScout template. The merchant scopes which products go in through that sub-feed's settings (filter by category / vendor / tag / selection / explicit product list — see [[apps-xml-feed]]). **There is no per-product "exclude from AdScout" toggle** on the product itself; opt-out is via the sub-feed filter.

### Push frequency: product feed refreshes every 4h; orders sent in real-time

Two queue mappings drive the data flow:
- **Product CSV** (`xml_feed_upload_ad_scout`) — regenerates every `14400s` = **4 hours**. AdScout pulls from CloudCart's URL on its own schedule.
- **Order push** (`xml_feed_adscout_order`) — fires immediately on every order event, queued to a system queue (5 min default tick). So order data is **near-real-time**; product data is refreshed at 4h cadence.

### Order events tracked: 4 lifecycle events

The integration listens to FOUR order events and pushes to AdScout's track-order endpoint:

| Event | What fires |
|---|---|
| `OrderCreated` | New order placed — sends as `type=1` (new order) with the `AdScoutAdsRef` cookie value as `adsRef` |
| `OrderStatusChange` | Order status changed — sends as `type=2` (status update) with new status |
| `FulfillmentAdd` | Order shipped / partially fulfilled — sends as `type=2` with fulfillment status |
| `FulfillmentRemove` | Fulfillment reversed — sends as `type=2` with updated fulfillment status |

The cookie `AdScoutAdsRef` is ONLY relevant on the first `OrderCreated` event — it ties the order back to the AdScout-sourced click. After dispatch, the cookie is unset. Subsequent status/fulfillment events don't need the cookie because AdScout tracks the order by its CloudCart order ID.

### Cookie attribution: missing cookie = no tracking

The `OrderCreated` push only fires when BOTH conditions are true: `type=1` AND `cookie != empty`. If the customer arrived organically (no AdScout cookie), the order is NOT tracked, even though the merchant has AdScout active. So AdScout's stats reflect only **cookie-attributable** orders — direct customers, returning customers without a recent AdScout click, and customers in private-browsing won't appear in AdScout's revenue reports.

### Both queues are 4-hour intervals (not 4h feed + real-time orders)

Per the queue config:
- `xml_feed_upload_ad_scout` → interval `14400s` (4 hours) on `export` queue.
- `xml_feed_adscout_order` → interval `14400s` (4 hours) on `system1` queue — NOT real-time.

So **order data is also delayed up to 4 hours**, contrary to what "near-real-time" suggests. Status changes and fulfillment events queue into `system1` and get processed on the system's tick cadence — typical lag of minutes to hours depending on queue depth. Merchants expecting instant AdScout dashboard updates after a sale should adjust expectations.

### Plan-tier check on order push job

The SendOrder job inherits `PlanLimit` trait — it checks `$site->plan_expired` before sending. If the site's plan has expired, the job returns `SITE_PLAN_EXPIRED` and skips the push entirely. The merchant who lets their plan lapse will see AdScout tracking go silent.

### Maintenance-mode block

The job also checks `$site->maintenance` and returns `SITE_MAINTENANCE` if true. Orders placed during maintenance windows aren't pushed to AdScout (they wouldn't have been placed under maintenance anyway, but if maintenance is toggled retroactively, the queued jobs skip).

### Pricing model: not enforced by the integration

Per the code: there's no logic in CloudCart that handles cost-per-click, cost-per-acquisition, or listing fees. **AdScout's commercial model is between the merchant and AdScout**; the integration only pushes catalog + order data and trusts AdScout for billing.
