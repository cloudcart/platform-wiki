# Google Search Console

## Purpose

**Google Search Console (GSC)** integration — connects the storefront to Google's webmaster portal where Google reports indexing status, search queries that drove traffic, crawl errors, mobile usability issues, structured data validation, sitemaps, and security alerts. Essential for SEO monitoring.

The integration's primary function is **site verification** — adding the merchant's storefront to their GSC property so Google trusts the domain ownership.

## Where to find it

Sidebar → Apps → install → **Google Search Console**. See [[apps-google-search-console-settings]] for verification setup.

## What the merchant can do here

- Configure GSC verification.
- Inject a verification meta tag into the storefront's `<head>` (via the `getMeta` method).
- View verification status.

### What the merchant CANNOT do here
- View search analytics data — that's in the GSC console at search.google.com/search-console.
- Submit sitemaps from here — done in GSC console.
- Get search-query reports inside CloudCart — read-only outside CloudCart.

## Settings & fields

The Manager exposes:
- `getMeta` — returns the verification meta tag string (e.g., `<meta name="google-site-verification" content="..." />`) that CloudCart injects into the storefront's `<head>`.
- the configured check — verification-tag presence check.

### Verification methods

Google Search Console itself supports several verification methods (meta tag, HTML file, DNS TXT, Google Analytics property), but **CloudCart's GSC app only implements the meta-tag method**. The other methods are not supported here — to use DNS or file-upload verification the merchant must do that work outside CloudCart (the file would need to be served by the storefront infrastructure; DNS handled at the registrar).

## Business rules

### Sets the verification tag

When the merchant configures the verification code (provided by GSC), CloudCart injects it as a meta tag on EVERY storefront page. Google's crawler reads the tag and confirms ownership.

### One verification at a time

Each GSC property requires one verification method. Multiple methods can verify the same property (redundancy).

### Required for many SEO actions

Once verified, the merchant can:
- Submit sitemaps to Google for faster indexing.
- See Performance reports (queries, clicks, impressions).
- See Coverage / Indexing reports.
- Set up email alerts for security / manual-action issues.

### Permission

Standard apps permission scope.

## How it works (verified against backend)

### Single required setting: `meta_tag`

The integration requires only the `meta_tag` field. The merchant pastes Google's verification meta tag (or just the content value).

### Meta tag injection gated by install + active

The platform returns the meta tag for injection **only when the app is installed AND active**. Toggling the app inactive immediately removes the verification tag from the storefront (next page load).

**Confirms: STRICTLY meta-tag-based verification** — no OAuth, no GSC data pulled into CloudCart. The integration is push-only (CloudCart → Google) for verification; reading GSC data requires the merchant to visit search.google.com directly.

### Minimal scope: verification only

The integration is minimal — just an app key, a configured-check, and a getter for the meta tag. NO functionality for:
- Fetching search-query data.
- Submitting sitemaps programmatically.
- Reading indexing status.
- Pulling Coverage reports.

This is a VERIFICATION-ONLY integration. Full GSC management still happens in Google's own UI.

### Sitemap is generated by CloudCart's own Sitemap helper, exposed via routes

The sitemap is produced by the platform's sitemap helper (split by content module via the `sitemap.included` config) and is exposed on the storefront as `sitemap/<name>/<page>.xml`. The merchant submits this URL to GSC manually inside Google's UI — there is no API call from CloudCart to GSC that says "here's my new sitemap". The Sitemap helper does include ping endpoints (Google webmaster ping, Yahoo, Ask) it CAN call, but submission timing is determined by the Sitemap helper, not by this Search Console app.

### Multi-property support is single-property

The integration stores ONE `meta_tag` value per store. Merchants verifying multiple GSC properties (e.g., `https://store.com` + `https://m.store.com`) typically need one verification method per property; CloudCart's app supports only one tag-based verification at a time. The merchant either uses a different verification method (DNS or HTML file) for additional properties, or verifies them in Google's UI without CloudCart's help.

### HTML validation runs on the meta tag input

When the merchant pastes the verification snippet, the platform parses it as HTML to confirm it's valid. Pasting malformed text fails save with "Code must be a valid HTML". Pure whitespace / empty also fails since the meta tag is required for the app to be configured. Alternative GSC verification methods (HTML file, DNS TXT, GA-based) are NOT handled by CloudCart — only meta tag is supported here.

### No GSC data pulled into CloudCart reports

The integration is strictly outbound (CloudCart presents the verification tag to Google) — there is no OAuth flow that would let CloudCart call GSC's API to read search-query / impressions / clicks data. To see search analytics, the merchant logs into search.google.com directly.

### Marketing Setup checklist queries this app for "configured" state

The Marketing Setup checklist (under [[marketing]] modules) checks for the GSC verification step by reading a separate setting (`google_search_console_verification`) and the merchant's manual checkbox (`marketing_step_status_google_search_console`). The platform DOES auto-detect when GSC verification is set, even if the merchant hasn't manually ticked the checklist item — that auto-detection is what feeds the Marketing Setup wizard's "complete" indicator.

### Meta tag accepts either the full snippet OR just the content value

The `meta_tag` setting stores whatever the merchant pastes. The `getMeta` method returns that raw value to the template. If the merchant pastes the FULL meta tag (e.g., `<meta name="google-site-verification" content="ABC123" />`), the storefront emits exactly that. If they paste just the content value (`ABC123`), only that value is emitted — which Google's verifier will NOT accept. The ValidHtml rule only enforces "must parse as HTML", which accepts both forms; merchants who paste only the token value will pass save but FAIL verification at Google's end.

### Storefront uses `getMeta` only when the app is installed AND active

Toggling the app off (`active=0`) without uninstalling immediately removes the verification tag from new page loads. Google's next crawl will see no tag → verification revoked. The merchant should keep the app **active** for verification to remain valid.

### Vue UI is a single Edit box (inline edit)

The Vue Settings page renders a SINGLE settings box via `SettingsBox` with `editMethod: 'inline'` — the merchant clicks Edit inline, the text field appears in-place (no slide-over modal). The single field is labeled "Meta tag" with placeholder showing the full meta tag format: `<meta name='google-site-verification' content='XXXX_XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX'>`. The field type is `text` (multi-line capable).
